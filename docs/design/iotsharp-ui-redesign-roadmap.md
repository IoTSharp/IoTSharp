# IoTSharp 界面重构路线图

## 目标与边界

本轮把 IoTSharp 从旧式后台皮肤升级为 **XJETC Ops Acrylic Control Plane**。目标是让界面直接说明平台能力、业务对象和运行证据，同时保留现有 Vue 3、Vite、Element Plus、Fast Crud、路由、权限和 API 契约。渐变、毛玻璃和亚克力只作为导航上下文与浮层材质，不成为数据表格和表单的背景。

本轮不做全量重写，不删除 `NSwag.AspNetCore`、`RulesEngine`、`Jint`，不把长时发布流程塞入 RuleChain，也不把 Device 当作 Asset 层级或发布范围。

## 2026-09 监测工作流优先级

用户已确认设备状态监测、AI 和预测运维方向，以已有状态上报的高速公路收费系统验证。下一轮设计保留现有外壳、12 套主题和技术栈，优先把当前功能变成可完成现场任务的工作流。详见 [定位与实施规划](../strategy/2026-09-device-health-strategy.md) 和根路线图 #100~#171。

页面实施要求：

1. 以设备和现场状态替换介绍“本页面如何设计”的文案，减少重复摘要和说明卡，将异常表、证据和明确动作放到工作区前部。
2. 继续复用 ConsolePageShell、ConsoleCrudWorkspace、ConsoleDrawerWorkspace；新增健康表、状态/质量标签、时间线和版本比较组件，仅在真实重复出现时抽象。
3. Edge 的 Target/Current/Hash/Receipt 等字段使用中文业务标签；完整 ID、哈希和 JSON 放入可展开高级视图，保留复制与诊断能力。
4. 筛选、排序、列选择和时间窗可恢复；详情可分享；错误、部分成功、权限不足、未知、维护中、离线缓存均有专门状态。刷新不能清除选中项和用户正在查看的证据。
5. 保持桌面表格密度、固定列和响应式约束。移动端优先展示异常与现场确认；本次 390px 首页虽然没有页面级横向溢出，但首屏主要是摘要，不能以此认定移动诊断已经可用。
6. 图表使用固定时间窗、聚合及点数上限，图例不得被裁切；按需加载重型编辑器。状态色不随主题改变；凭据处理必须在 API/导出/日志及 AI 边界共同落实。
7. 继续保留 Asset View/3D 投资，但首批验收用二维站/车道状态矩阵、列表和趋势完成任务，不把大屏或三维建模作为监测前置。

验收按真实任务记录结果：定位异常设备、辨别旧数据、追溯站点共因、查询告警、比较配置、确认回滚后状态、记录维护结果。结合桌面/移动截图、键盘焦点、权限矩阵及 API 合同验证；不使用演示数字或只看视觉截图代替任务验收。

## 分阶段实施

### 阶段 0：领域语言收敛

1. 逐页检查标题、按钮、字段、空状态和错误提示，确保 Product 是能力模板、Device 是运行实例、Asset 是业务对象。
2. 把旧页面中混用的 Produce、DeviceGroup、站点树和发布范围用词替换为当前领域概念。
3. 为每个高风险操作保留权限提示、确认、审计入口和失败后的回滚上下文。

验收证据：路由清单、API DTO 与页面文案对照表；不需要演示数据即可解释每个页面的业务对象。

### 阶段 1：Edge/Gateway 运行基础

1. 使用真实 Gateway/EdgeNode 完成注册、心跳、版本和能力上报。
2. 在 EdgeNode 详情中展示当前状态、能力声明、采集分配、任务接收、执行结果、失败、超时和诊断上下文。
3. 将 Gateway 的南向协议能力与 EdgeNode 的运行时生命周期分开显示，但在同一运维工作区提供关联入口。

验收证据：真实运行时日志、注册与心跳时间线、能力报告、任务 receipt/result、租户隔离和审计记录。

### 阶段 2：Collection Template 建模

1. 建立协议模板、连接模板、点位模板、转换链、采样策略和映射策略的可复用页面。
2. 将模板归属于 Product 或模板库；生成不可变配置版本并关联运行时目标。
3. 在设计器中提供预览、校验、差异和人工确认，不直接覆盖生产配置。

验收证据：批准的模板、不可变版本号、部署前后差异、运行时当前/目标版本收敛记录。

### 阶段 3：Release Center

1. 为 OTA、采集器软件、固件和配置建立独立包与版本视图。
2. 支持目标范围、灰度批次、审批、任务下发、确认、暂停、失败、回滚和结果审计。
3. 以 EdgeNode、Gateway 或选定 Device 作为运行目标，以 Asset 作为业务范围时显式标注两者关系。

验收证据：一次受控 canary 发布和一次回滚，完整保留目标、审批、任务、接收、结果和回滚后的状态。

### 阶段 4：RuleChain 可观测性

1. 增加节点库、版本、模拟输入、执行追踪、审计和背压指标。
2. 保持 RuleChain 面向实时处理，不加入 OTA、发布、审批等长时工作流。
3. 为脚本节点提供可解释输入输出和失败定位，减少脚本依赖但保留兼容能力。

验收证据：规则版本差异、一次模拟运行、节点级追踪、失败重放和权限审计。

### 阶段 5：设计系统与 AI 辅助

1. 将 `DESIGN.md` 和 `.impeccable/design.json` 作为新增页面的视觉契约；共享工作区优先复用 `ConsolePageShell`、`ConsoleCrudWorkspace` 和 `ConsoleDrawerWorkspace`。
2. 继续补齐表格、表单、抽屉、空状态、错误状态、加载态、键盘焦点和 `prefers-reduced-motion`。
3. AI 只通过授权技能与 MCP 调用控制面能力；先做只读的边缘诊断、点位映射建议、规则解释和发布问答，高风险操作必须人工确认并写入审计。

验收证据：主题矩阵截图、桌面/移动端截图、可访问性检查、权限矩阵、AI 工具调用审计和人工确认记录。
